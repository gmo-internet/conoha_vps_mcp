## 16. Taste Invariants（主観的品質基準）

機械的に検証困難だが、プロジェクトの品質と一貫性に重要な判断基準。
L2（CLAUDE.md + Claude Code Review CI）で執行する。

### APIレスポンス設計

- フォーマッターは「ユーザーが次のアクション判断に必要な情報のみ」に絞る
- 不要なネスト（`server.server.id` → `server.id`）を排除する
- 日付や状態値はそのまま返し、独自フォーマットを加えない

### エラーメッセージ

- 「何が起きたか」+「何をすべきか」の2要素で構成する
- 例: `"サーバーが見つかりません。server_idが正しいか確認してください"`

### 関数設計

- 1関数 = 1 API操作（単一責任）
- 複数APIを組み合わせるオーケストレーションはクライアント関数に持たせない
- 副作用（ログ出力等）は最小限に

### セマンティックルールとの関連

以下のL2ルールはこの品質基準を具体化したもの:

| ID | ルール | 判断基準 |
|----|--------|---------|
| B-5 | `executeOpenstackApi()` → `formatResponse()` チェーン | 単一責任: API呼び出しとレスポンス整形を分離 |
| B-6 | storageは `generateApiToken()` を直接使用 | アーキテクチャ例外の明示的管理 |

## PR前セルフチェック観点（過去クローズPRレビュー由来）

過去のクローズ済みPR（レビュー付き53本）のレビューを総ざらいし、レビュアー（主に @s-hirano-ist）が
繰り返し問うてきた観点をセルフチェックとして抽出したもの。**PR作成前に著者自身がこの目線で自己点検し、
レビュー指摘を先回りして解消する**。各観点に目的（なぜ気にするか）と代表的な出典PRを併記する。

> レビュアーの指摘は ask/suggestion 中心で語調は柔らかい（「〜してほしいかも」「m(_ _)m」）が、
> 影響の大きいものは「別PRで」と落とし所を調整しつつ最終的にほぼ全件対応に至っている＝**事実上の must**
> として機能する。下記をPR前に潰しておくことでレビューの往復を減らす。

### 1. 棚卸し: 「なぜ在るのか」説明できないものは残さない（最頻出）

- [ ] 追加・変更した設定 / `.gitignore` エントリ / 環境変数 / 依存は、存在理由を一言で説明できるか
- [ ] 参照されていない設定・未実装のまま残った環境変数・機能巻き戻しの取り残しはないか

目的: 最小構成への収束とデッドコード排除。説明できないものは削除候補。
出典: #414（`.gitignore` / `knip.json` / `biome.json` / `.env.example` への「?」一言 → 未参照設定・未実装 env var を削除）。関連: `file-structure.md`、B-5/B-6 の単一責任。

### 2. 依存・ツールチェーン: 固定しつつ最新へ追従

- [ ] devDependencies は `^` なしの固定バージョンか
- [ ] ランタイム/フレームワーク（React・TypeScript target 等）は最新に追従しているか。下げる場合は理由を明示したか
- [ ] 役割の重なるビルドツール（例: vite と esbuild）が併存していないか

目的: 再現性の担保と最小依存の両立。
出典: #410（devDeps を固定値へ / TS target 2022→最新 / vite・esbuild の重複）, #421（React v19 へ）。

### 3. 型安全: 安易な `as` キャストを避ける

- [ ] `as` キャストを使っていないか。zod 検証や `.ts` fixture 化など型安全な代替で置き換えられないか

目的: ランタイム不整合の予防。出典: #410（mock-data の `as` cast → zod 検証 / `.ts` 化）。

### 4. 関心の分離・アセット外部化

- [ ] HTML と CSS、ロジックとアセットが適切に分離されているか
- [ ] アイコン等のアセットは埋め込みでなく独立ファイル（svg 等）として import しているか

目的: コード上で意図が直感的に見え、密結合を避ける。
出典: #414（`mcp-app.html` の CSS 分離）, #421（Icon を svg ファイルへ外部化）。

### 5. 変更意図の明示（セルフ注記）

- [ ] 各 diff が「挙動変更」か「リファクタ/体裁のみ（挙動不変）」かを、PR本文またはコメントで明示したか

目的: レビュー負荷の低減。挙動変更とノイズ変更の分離。
出典: #101（`src/index.ts` を「リファクタリング」、`csv-to-markdown.js` を「体裁のみ」と自己注記）。

### 6. ドキュメント充足

- [ ] 新規の環境変数・UI 機能・公開仕様は、コードだけで自明にせず説明（必要ならユーザー向けドキュメント）を添えたか

目的: 利用者・レビュアーが意図を理解できる状態を保つ。
出典: #414（`.env.example` の環境変数説明 / ユーザー向けドキュメント追加の要請）。

### 7. リリース/CI の堅牢性と最小権限

- [ ] リリース確定の発火条件（例: `release/vW.X.Y(-rc.Z)` ブランチの main 宛マージ）を曖昧にしていないか
- [ ] GitHub Actions のトークン権限は最小限か。private/public 双方のリポジトリで動作するか

目的: 誤リリースの防止と権限分離。
出典: #22（専用トークンへ切替）, #33（`issues: write` を必要分だけ追加）, #101（publish のブランチ命名規約を明記）。

### 8. OSS 公開物の正しさ

- [ ] ライセンス定型文・NOTICE・配布物（`npm pack` / `.mcpb` の中身）に欠落や余計な混入がないか

目的: 公開・配布物のコンプライアンスと体裁。出典: #35（Apache ライセンスの著作権定型行を残す提案）。
